## Blockers — must do before Wednesday

### 1. 🔧 `base-image/config.yaml` points at a dead cluster
The enrollment endpoint is `agent-api.modern-recon.apps.cluster-4cmzl.dynamic2.redhatworkshops.io`.
The new cluster will have a new CA and enrollment cert. Regenerate against the
new Edge Manager and get it onto the device. Two ways:

```bash
# on your laptop, logged in to the NEW service
flightctl certificate request --signer=enrollment --expiration=365d --output=embedded > base-image/config.yaml
```

- **Fast path (device already installed):** don't rebuild anything —
  ```bash
  scp base-image/config.yaml redhat@<jetson>:/tmp/ && ssh redhat@<jetson> \
    'sudo install -m 0600 /tmp/config.yaml /etc/flightctl/config.yaml && sudo systemctl restart flightctl-agent && sudo journalctl -fu flightctl-agent'
  ```
  `/etc` is persistent on bootc, so this survives reboots. Then approve the
  enrollment request in the new UI.
- **Clean path (fresh install on stage):** rebuild base image → ISO → USB with
  the new config.yaml baked in. Only do this if you also want the base-image
  changes below (i2c-dev, :8080) *and* you have a spare afternoon.

### 2. 🔧 Agent version vs. new service version
The base image installs `flightctl-agent` from `rpm.flightctl.io` (upstream,
whatever was current on 2026-06-18). The new cluster's Edge Manager may be a
different version. Check both and make sure the agent is not newer than the
service:
```bash
ssh redhat@<jetson> 'flightctl-agent version'        # or rpm -q flightctl-agent
flightctl version                                     # client + server
```
If the agent is newer, downgrade the RPM in the base image to match (or use the
RHEM-shipped agent RPM) and rebuild. If older, it's usually fine.

### 3. ✅ OS image reference mismatch (would reboot the Jetson mid-demo)
Three different image names were in play:
- kickstart `bootc switch … quay.io/rh-ee-soanders/mangey-moose-base-image:latest`
- fleet specs `os.image: quay.io/rh-ee-soanders/mangey-moose:latest`
- README build step pushes `mangey-moose:latest`

If `spec.os.image` in the fleet doesn't match what the device booted, the agent
performs an OS update (bootc switch + reboot) on first reconcile — or fails the
rollout if the image isn't pullable. **The `os:` block is now commented out in
all three fleets.** Re-enable only once it matches, exactly:
```bash
ssh redhat@<jetson> 'sudo bootc status --format json | jq -r ".status.booted.image.image.image"'
```

### 4. 🔧 Fleet YAML schema vs. the new server
Specs are `flightctl.io/v1alpha1`. flightctl-demos moved to `v1beta1`. First
thing after `flightctl login` to the new cluster:
```bash
for f in fleet-specs/fleet-{yolo,traffic,imu}.yaml; do flightctl apply --dry-run -f $f; done
```
If it complains, it'll be `apiVersion` and/or the `applications[].inline`
wrapper keys — the structure is otherwise the same.

### 5. ✅ Kickstart `%post` would abort the install
`hostnamectl set-hostname` needs dbus, which doesn't exist in the Anaconda
chroot; with `set -e` + `--erroronfail` that kills the install. Replaced with
`echo … > /etc/hostname`. Also guarded the `video` group append so it can't
duplicate the line. (This only matters if you reflash.)

### 6. ✅ README told you to label the device with the wrong key
README said `purpose=drone-edge`; every selector says `purpose=mangey-moose`.
Also `flightctl get fleet drone-edge-yolo` → `mangey-moose-yolo`. Fixed.
Following the old README literally would have produced a device that matched
no fleet and a very quiet demo.

### 7. 🔧 Registry auth for private quay repos
If `quay.io/rh-ee-soanders/*` is private the agent can't pull. Either make the
five app repos public for the week, or add `/etc/containers/auth.json` via the
fleet `config:` block. Check on the device: `sudo podman pull quay.io/rh-ee-soanders/mangey-moose-mediamtx:v1.17.1`.
